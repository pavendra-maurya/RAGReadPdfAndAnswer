## 1. Summary for the customer

The Admin console is served by **ws_TunnelService** (Secure Gateway, port 443). Every new HTTPS connection gets a TLS handshake on a small, fixed pool of **30 worker threads**.

On 2606, a worker thread can get **stuck forever** when a client opens a connection to port 443, starts the TLS handshake, and then goes silent. Typical causes are a laptop going to sleep, a Wi-Fi or VPN drop, or a firewall silently dropping an idle session. Three things together make the hang permanent:

* The socket has no read timeout during the handshake.
* The built-in "kill a slow handshake" mechanism cannot unblock the thread.
* The 5 helper threads that try to close those connections get stuck as well.

Each stuck connection permanently uses up one of the 30 threads. After enough of them, the pool and its 30-slot queue are full. The thread that accepts new connections on port 443 then spins (using CPU) and **stops accepting connections**. Windows rejects new connection attempts once the listen backlog fills, so the browser shows **ERR_CONNECTION_REFUSED**, even though every Horizon service still shows *Running* and port 443 is still owned by `ws_TunnelService.exe`. Restarting the service clears the stuck threads, so the problem returns after the same number of "bad" client connections. That can take minutes or hours depending on how many internal clients there are.

Internal nodes are affected because they take TLS connections **directly** from hundreds of end-user devices. External nodes only receive connections from UAG, which completes or cleanly closes its handshakes.

**The netstat confirms this and finds the "every 15 minutes" trigger (section 2.5):**

* Exactly **30 long-lived ESTABLISHED** connections on 443 were accepted by the tunnel and never finished. That is one per worker thread.
* **12 of those 30 (40%) come from the Connection Server itself** (`22.1.11.95 → 22.1.11.95:443`). Some local process on the server opens a TCP connection to its own port 443 **every 15 minutes, at xx:01:44, xx:16:44, xx:31:44 and xx:46:44**. It **never sends a TLS ClientHello** and **never closes the connection**. Each one permanently consumes a worker thread. This process does not log to the Horizon debug log; it is most likely a monitoring or port-check agent or a scheduled script.
* The remaining 18 stuck connections come from internal end-user devices.
* After 13:47 the tunnel stopped accepting. 50 more connections sit un-accepted in the Windows listen backlog.
* 57 sockets are in **CLOSE_WAIT**. These are clients that gave up waiting (including the admin's own `https://localhost/admin` attempts) while the tunnel never closed its side.

**Workaround (no code change):** add a JVM option to ws_TunnelService that limits how long a TLS handshake may take (`-Dorg.bouncycastle.jsse.handshakeTimeoutMillis=15000`). See section 6. **In addition**, identify the local process that connects to its own port 443 every 15 minutes and stop it or correct it (section 6.2). That alone removes about 40% of the leak on this node.
**Permanent fix:** a code change in the `simple.http` connector (section 5). **It is not in 2609 or `main`** (section 4.3). Upgrading to 2609 / PR #8805 will **not** fix this.

What this proves:

1. **The cancellation and close never worked.** All 5 connections that the terminator "cancelled" (10:40–10:46) are **still ESTABLISHED 3.5 h later**. `PooledProcessor.cancelledExecution()` → `ensureSockClosed()` → `sock.close()` (`PooledProcessor.java:148, 196`) never completed: it is blocked on the BC socket monitor held by `startHandshake()`, as described in section 3.2. This confirms H1 directly from the operating system's view.
2. **The client side of each stuck connection also stays open.** For the self-connections both ends are visible: `22.1.11.95:50588 → 22.1.11.95:443 ESTABLISHED` and `22.1.11.95:443 → 22.1.11.95:50588 ESTABLISHED`. The client process is still holding its socket. These are not half-open connections from a crashed or sleeping device. The client deliberately keeps the TCP connection open and sends nothing.

#### 2.5.2 The 15-minute self-connector (the periodic trigger)

* The CS connects **from its own IP to its own port 443** every 15 minutes, at the same second offset: **xx:01:44, xx:16:44, xx:31:44, xx:46:44**. Log evidence:
  * PID 0x2674: 09:31:44, 09:46:44, 10:01:44, 10:16:44.
  * PID 0x192C: 10:46:44, then every 15 minutes through 13:46:44.
  * The schedule carries straight across the service restart, so the client **is not part of ws_TunnelService**.
* **It never sends a ClientHello.** After each of these accepts there is no `KeyVaultKeyManager` / `Removing root certificate from chain` / `BCJSSE-HandshakeCompleted` activity for that connection. Checked at 10:46:44, 11:46:44 and 13:16:44; the next pool-3 activity always belongs to a different peer. So the pool thread blocks in `TlsServerProtocol.accept` waiting for the very first record, and with SO_TIMEOUT 0 that wait never ends.
* **It doesn't log anything in any Horizon component** at those times: no broker (1E40/2218), tunnel or perfmon line other than the accept. `SGHealth` (`broker/.../health/SGHealth.java:794-842`) runs about every minute over JMS and is not it. No 15-minute HTTPS self-call was found in broker, tunnel, common or rest code. **It is most likely a third-party monitoring or port-check agent or a scheduled script on the CS** that does a TCP connect to `<FQDN>:443` (the FQDN resolves to 22.1.11.95, hence the hairpin) and leaks the socket. Identify it with the commands in section 6.2.
* **Impact:** **12 of the 30 stuck threads (40%)** on this node come from this one source. On its own it exhausts the 30-thread pool in **7.5 hours**. Combined with end-user devices it did so in about 3 hours here. This is also very likely the "periodic ~15 min" pattern R&D observed.

#### 2.5.3 Other stuck peers

The other 18 stuck connections come from internal end-user subnets: 22.1.x, 22.11.39.x, 22.22.100.x, 22.8.33.x and 192.168.1.x. `22.11.39.135` alone holds 9 ESTABLISHED and 5 CLOSE_WAIT sockets (it does `POST /broker/xml`, i.e. a Horizon Client). No UAG or load-balancer addresses appear.

#### 2.5.4 CLOSE_WAIT (57) explained: the tunnel never closes queued sockets

* **18 accepted + CLOSE_WAIT** (accepted 13:41:09 → 13:47:10). These were waiting in the despatch queue (`ArrayBlockingQueue(30)`, `Despatcher.java:81`) for a free thread that never came. The client gave up and sent FIN, but no thread ever touched the socket, so the server side sits in CLOSE_WAIT. It includes **6 × `127.0.0.1` (13:45:57–13:46:02)**: the admin trying `https://localhost/admin` on the server. Their client side is `FIN_WAIT_2`. This matches the log's `handshakes=25` at 13:46:23 and `pool full` at 13:47:10.
* **39 not accepted + CLOSE_WAIT** (plus 11 ESTABLISHED) are in the **OS listen backlog**. The kernel completed the TCP handshake, but the accept thread has been spinning in `MonitoredPool.despatch` since 13:47:10 and never called `accept()` again. Most of them (29) are from **22.22.100.129, an admin workstation whose Admin console dashboard polls `/rest/monitor/v2/system-metrics`, `/rest/monitor/v1/sessions/metrics` and `/rest/monitor/v1/health-metrics`**. Its browser kept retrying. At 13:54 it fell back to **port 80** (`Accepted connection on port 80 from /22.22.100.129`).
* **This CLOSE_WAIT is a symptom, not the cause.** It is not the `PollerInputStream`/`BasicPoller` leak suspected in R&D's hypothesis (H4). Those sockets were never handshaked or polled.

#### 2.5.5 What the browser sees

`socketBacklog` = **200** (`NetHandler.java:160-169`, logged `Socket back log has been configured with a value of 200`), passed to `ss.bind(socketAddress, backlog)` (`NetUtil.java:589`). At 14:07 the backlog held 50 entries.

* While the backlog has room, Windows completes the TCP handshake, but the tunnel never answers the ClientHello. Browsers then show a timeout or a closed connection.
* Once the backlog is full, or Windows' SYN-backlog protection triggers, new SYNs get a RST, which the browser reports as **ERR_CONNECTION_REFUSED**.
* Which of the two a user sees depends on how long the outage has lasted and on how many clients are retrying. **The root cause is the same in both cases: the accept thread is no longer calling `accept()`.**

## 3. Code analysis (release/2606)

### 3.1 The 443 listener and accept loop

| Step | Code |
|---|---|
| Listen backlog = `socketBacklog` (locked.properties), default **200** | `tunnel/tunnel-server/src/main/java/com/omnissa/vdi/ice/server/NetHandler.java:160-169` |
| SSL server socket for 443 created (BC JSSE `ProvSSLServerSocket`) | `NetHandler.java:239-243` (`NetUtil.makeSSLListener(...)`) |
| Front wires the simple.http connector and congestion monitor | `tunnel/.../front/Front.java:2259-2290` (`handshakeLifetime` default 10 s: `Front.java:491, 2670-2690`) |
| `connection.connect(serverSocket)` → `new Processor(...)` (thread "HTTPS Connection Processor") | `Front.java:2373`, `thirdparty/simple-3.1.3/src/simple/http/connect/Connection.java:113-117` |
| Accept loop | `simple/http/connect/Processor.java:155-182` (`run`) and `198-316` (`execute`) |
| `sock = server.accept()` | `Processor.java:210` |
| SSL sockets handed to the pool | `Processor.java:281-289` → `Despatcher.getInstance().despatch(...)` |
| Rate-limit sleep (200 ms) when congested | `Processor.java:312-314` |

**What the accept loop does on failure:**

* `run()` catches **every `Throwable`** from `execute()`, logs `Problem with HTTP listener`, and loops (`Processor.java:158-181`). An OOM/`Error` doesn't kill the thread.
* It **exits** only if `server.isClosed()` (`:164-166`) or the throwable is an `SSLException` (`:168-179`). In that case it logs **FATAL** `Connection Processor is exiting`, **closes the server socket**, and returns. The process stays up and 443 is then really closed, which would also cause ERR_CONNECTION_REFUSED. **Neither message is in the logs**, so this path did not happen here (H3).
* **Full or rejected executor:** this is what happened. `Despatcher.despatch()` is `synchronized` (`pool/Despatcher.java:125`) and calls `MonitoredPool.despatch()`, which loops **`while (status == null)`** on `RejectedExecutionException` with **no sleep, back-off or give-up** (`pool/MonitoredPool.java:251-347`, catch at `:255-281`). Until a pool slot frees up, the accept thread never returns to `server.accept()`. It is not *dead*, it is **spinning**, which explains the sustained ~30% CPU. The only log line is the rate-limited `Connection processor pool full` (`PooledProcessor.java:121-131`, quash 120 s).

### 3.2 `PooledProcessor.run()` / `handshake()` (questions in item 2)

| Question | Answer with code |
|---|---|
| Pool size / queue / handler | `THREADS = 30`, `TASKS = 30` (`Despatcher.java:45-50`). Can be overridden with `-Dsimple.http.connect.pool.poolsize` / `.queuesize` (`:73-78`). Queue is `ArrayBlockingQueue(30, fair)` (`:81-82`). `MonitoredPool` uses core = max = 30 because keepAlive = 0 (`MonitoredPool.java:99-100`). Default `ThreadPoolExecutor.AbortPolicy` → `RejectedExecutionException` → retried forever (`MonitoredPool.java:251-281`). Threads use the default factory, so they are named `pool-3-thread-N`. |
| Handshake / read timeout? | **None.** `run()` calls `configure(sock)` and then `handshake(sock)` (`PooledProcessor.java:178-191`). The configurator in production is `CustomConfigurator` (log line at 10:37:03; selected via `ConfiguratorFactory.java:53-63`). It does **`s.setSoTimeout(0)`** and **`s.setKeepAlive(false)`** (`CustomConfigurator.java:54-56, 88-93`). `secure.startHandshake()` (`PooledProcessor.java:244`) therefore blocks **with no time limit**. BouncyCastle 1.85's own handshake timeout, `org.bouncycastle.jsse.handshakeTimeoutMillis`, defaults to **0 = disabled** (bctls-jdk18on-1.85 `ContextData.<init>`: `getIntegerSystemProperty("org.bouncycastle.jsse.handshakeTimeoutMillis", 0, 0, MAX)`). It is not set (not in the logged system properties). (`DefaultConfigurator` would set 60 s, `DefaultConfigurator.java:41-44`, but HZN-929 deliberately replaced it, commit `f12444044f`.) |
| Can the "handshake lifetime" (10 s) rescue the thread? | **No.** The watch list is only checked when a new connection is despatched (`MonitoredPool.java:315-346`). For an overdue task, `Monitor.terminate()` queues work on `terminatorPool` (`MonitoredPool.java:201-221`). That work calls `status.cancel(true)`, which is only `Thread.interrupt()` and **does not unblock a blocking socket read** on a platform thread. It then calls `PooledProcessor.cancelledExecution()` → `ensureSockClosed()` → `sock.close()` (`PooledProcessor.java:138-149, 193-200`). In BC JSSE, **`ProvSSLSocketDirect.startHandshake()` and `ProvSSLSocketDirect.close()` are both `synchronized`** on the socket (verified with `javap` on bctls-jdk18on 1.81, 1.83, 1.85 and 1.86.1). The handshaking thread holds that monitor while it blocks in the read, so **`close()` blocks forever too**. |
| Terminator pool | `Executors.newFixedThreadPool(5)` with an unbounded queue (`Despatcher.java:88-89`, added by HZN-5102 commit `5d6677b7d6`). After 5 blocked `close()` calls, **all 5 terminators are stuck** and later terminate requests just queue up. This is exactly what the logs show: 5 `pool-4-thread-1..5` "Overrunning … cancelled" lines and then nothing. The monitor entry is also removed (`delete(task)`, `MonitoredPool.java:343`), so the thread is never looked at again. |
| Queued (not yet started) tasks | Never treated as overdue (`Monitor.isOverdue()` returns `false` while `runUntil == 0`, `MonitoredPool.java:168-175`). They wait for a free thread indefinitely. |
| Socket always closed after failure? | **Only for `Exception`.** `run()` catches `Exception` and calls `ensureSockClosed()` (`PooledProcessor.java:182-190`). There is no `finally`. An `Error` (OOM, `StackOverflowError`, `NoClassDefFoundError`) skips the close. Tasks are submitted via `submit()` (`MonitoredPool.java:254`), so `FutureTask` captures the throwable and `afterExecute(r, t)` receives `t == null`. **`interruptedExecution()` (`MonitoredPool.java:417-424`, `PooledProcessor.java:155-169`) is effectively unreachable**, and in that case the socket leaks (CLOSE_WAIT once the peer closes). Not observed here, but it is a real gap. |
| Why do the peers never close? | If the peer sent FIN or RST, BC's read would return EOF or an error, the handshake would fail and the thread would be freed (this is the 38 `Failed to read record` cases). A thread stays stuck only when **nothing arrives**: a sleeping or roaming device, a VPN/Wi-Fi drop, or a firewall/NAT idle-timeout that silently drops state. `CustomConfigurator` disables TCP keepalive (`CustomConfigurator.java:55, 92`), so such half-open sockets are **never** detected. These sockets show as **ESTABLISHED** (not CLOSE_WAIT) in `netstat`. |

### 3.3 `PollerInputStream.available()` → `peek()` and `BasicPoller.process()` (item 3)

* `BasicPoller.process()` calls `data.available()` (`BasicPoller.java:90-92`). `PollerInputStream.available()` → `available(1)` → `peek(1)` (`PollerInputStream.java:189-191, 209-214`).
* `peek(int)` sets **SO_TIMEOUT = 1 ms**, performs a real `data.read(...)` on the BC `AppDataInput`, then restores the old timeout (`PollerInputStream.java:263-275`, read at `:234`). `InterruptedIOException` (timeout) is swallowed (`:242-243`). So `available()` **does** do a read on the TLS socket, but it is bounded to about 1 ms. It does **not** block a poller thread indefinitely, and it runs only after the handshake, when the BC socket monitor is no longer held.
* On `SocketException` (your trace #2, "An established connection was aborted…", raised by BC as `internal_error(80) Failed to read record`), the exception propagates out of `peek()`. The restore at `:272` is skipped (minor defect, harmless here). It reaches `simple.http.Processor.execute()`, which catches **`Throwable`** and calls **`poller.close()`** (`simple/http/Processor.java:94-107`) → `Pipeline.close()` → `sock.close()` (`Pipeline.java:243-249`). The poller worker loop also catches `Throwable` and continues (`simple/http/Processor.java:60-68`). **No socket or thread leak on this path.** Idle pipelines are closed by `FastGranularPoller.wait()` (`FastGranularPoller.java:160-191`).
* **Conclusion:** this path is **not** the cause (H4).

## 6. Customer workaround (no code change)

### 6.1 Recommended: enable BouncyCastle's handshake timeout for ws_TunnelService

BC 1.85 (shipped in 2606) reads the JVM system property **`org.bouncycastle.jsse.handshakeTimeoutMillis`** (bctls 1.85 `ContextData`, default `0` = off). When it is > 0, `ProvSSLSocketDirect.startHandshake(boolean)` wraps the socket input in `HandshakeTimeoutInputStream`, which applies SO_TIMEOUT for the rest of the handshake and restores the original value afterwards. A stalled handshake then throws `SocketTimeoutException`, `PooledProcessor.run()` closes the socket (`PooledProcessor.java:182-190`), and the thread is released. The terminator's `close()` also unblocks, because the monitor is released.

Steps (on each affected CS, in a maintenance window):

1. Open `regedit` and go to the tunnel JVM options value referenced in code (`CustomConfigurator.java:17-19`):
   `HKLM\SOFTWARE\Omnissa\Horizon\Plugins\wsnm\TunnelService\Params` → value **`JvmOptions`**. The code comment spells it `...\wsnm\tunnelService\Params\JvmOptions`. Registry keys are case-insensitive, but confirm the exact key on the server.
2. **Append** (do not replace; the value already contains `-Dsimple.http.connect.configurator=simple.http.connect.CustomConfigurator` and others), separated by a space:
   ```
   -Dorg.bouncycastle.jsse.handshakeTimeoutMillis=15000
   ```
   Use `120000` if smart-card / certificate authentication is enabled on this CS. PIN entry happens during the handshake; the cert-auth handshake lifetime is 100 s (`Front.java:497`).
3. Restart the **Omnissa Horizon Connection Server** service.
4. Verify in the debug log after restart:
   `[JMXServer] System property: org.bouncycastle.jsse.handshakeTimeoutMillis=15000`
5. Afterwards you should see occasional `Problem processing HTTP connection ... SocketTimeoutException` / `Read timed out` (normal, the stalled peer is dropped). You should **not** see `Overrunning connection processor`, `Connection processor pool full` or a sustained CPU rise.

This property only bounds the **handshake**. After the handshake BC restores the SO_TIMEOUT that `CustomConfigurator` set, so tunnel and Blast connections are unaffected. It also bounds outbound TLS handshakes made by the tunnel JVM, and 15 s is generous for those. **Validate on a lab CS first** (repro in section 8).

### 6.2 Identify and stop the 15-minute local self-connector (no code change, do this as well)

On this node, 40% of the stuck threads come from a process **on the CS itself** that connects to `<FQDN>:443` every 15 minutes (xx:01:44 / xx:16:44 / xx:31:44 / xx:46:44), never sends TLS, and never closes. Its client sockets are still open at 14:07 (`22.1.11.95:50588 … 54714 → 22.1.11.95:443 ESTABLISHED`). That means the owning process is still running and holding them, so it can be identified directly.

```powershell

# Look for scheduled tasks / monitoring agents running every 15 minutes
Get-ScheduledTask | Where-Object { $_.Triggers.Repetition.Interval -eq 'PT15M' } |
  Select TaskPath,TaskName,@{n='Action';e={$_.Actions.Execute + ' ' + $_.Actions.Arguments}}
```

Typical culprits: a monitoring agent's "TCP port 443" or "URL" check (SCOM, SolarWinds, PRTG, Nagios/NSClient++, Dynatrace or similar), a security or inventory scanner, or a PowerShell scheduled task that opens a `System.Net.Sockets.TcpClient` to the FQDN and never disposes it.

Remediation, in order of preference:

1. Make the check close its socket.
2. Use a proper HTTPS check against `https://<FQDN>/favicon.ico` (the Horizon health endpoint).
3. Stop the check on the Connection Servers.

This must be confirmed with the customer. **Note:** even after this is fixed, end-user devices still produce silent connections (18 of 30 here), so 6.1 is still required.

### 6.3 Interim / defence-in-depth (optional)

| Setting | Where | Effect | Caveat |

* **Change `handshakeLifetime`** (`Front.java:2674`). Cancellation can't unblock the thread, so the value doesn't matter.

| `pool-4-thread-1..5` (terminator) | `WAITING` in `LinkedBlockingQueue.take` | **`BLOCKED (on object monitor)`** in `ProvSSLSocketDirect.close` **`- waiting to lock <ProvSSLSocketDirect@X>`**, the same X held by a `pool-3` thread ← `PooledProcessor.ensureSockClosed(PooledProcessor.java:196)` ← `PooledProcessor.cancelledExecution(PooledProcessor.java:148)` ← `MonitoredPool$Monitor.lambda$terminate` |
| `BCJSSE-HandshakeCompleted-N` | Short-lived | Should be absent or idle |
| `Processor` poller threads (`simple.http.Processor`) | `TIMED_WAITING` in the scheduler dequeue, or briefly in `PollerInputStream.peek` | Not involved. If many are stuck in `PollerInputStream.peek` with SO_TIMEOUT 0, report it separately (would contradict section 3.3). |

**Hypotheses the dump rules in or out:**

* **H1:** 30 × `pool-3` in `startHandshake` + 5 × `pool-4` `BLOCKED` in `close` + accept thread in `MonitoredPool.despatch`.
* **H3:** there is **no** `HTTPS Connection Processor` thread at all, and the log has `Connection Processor is exiting`.
* **H4:** many sockets in **CLOSE_WAIT** plus threads in `PollerInputStream.peek`.

**Network snapshot at failure time** (PowerShell, as admin):

```powershell
$p = (Get-Process ws_TunnelService).Id
Get-NetTCPConnection -LocalPort 443 -OwningProcess $p | Group-Object State | Select Count,Name
Get-NetTCPConnection -LocalPort 443 -OwningProcess $p -State Established |
  Sort-Object CreationTime | Select -First 40 RemoteAddress,RemotePort,CreationTime
```

What to look for under H1 (the netstat from this incident already shows all of these, see 2.5):

* About **30 ESTABLISHED** sockets that are hours old (CreationTime). These are the 30 stuck handshake threads. Expect some to come from the CS's own IP (the 15-minute self-connector).
* Plus up to 30 more recent sockets for the queued tasks, which become **CLOSE_WAIT** once those clients give up.
* `Listen` still present.
* More sockets (ESTABLISHED or CLOSE_WAIT) that were never accepted: these are in the listen backlog. They don't appear in the tunnel's `Accepted connection` log.
* CLOSE_WAIT **is** expected here (queued and backlog sockets the tunnel never touches). It does **not** indicate the `PollerInputStream` leak (H4).

**Nothing here affects the 443 listener or the TLS handshake.** No `socketBacklog`, `handshakeLifetime`, congestion thresholds, or `simple.http.connect.pool.*` settings are set. This file does not cause or relieve the port-443 lock-up, and sections 2–9 still apply.

Two lines are wrong and should be fixed as separate hygiene items:

| Line | Problem | Effect | Fix |
|---|---|---|---|
| `portalhost.1..3` | The key is case-sensitive. `Ice.java` reads `config.getPropertyList("portalHost")`. `PropertiesConfigurationProperties` matches the regex `portalHost\.\d+`. | All 3 entries are **silently ignored**, so the portal-host set is empty. This only works because `allowUnexpectedHost=true` disables Host-header validation. | Rename them to `portalHost.1/.2/.3`. After that, try removing `allowUnexpectedHost=true`. |
| `hstsFlags` | `RequestInfo.addSecurityHeaders()` already emits `max-age=<hstsMaxAge>`, then appends the flags verbatim, quotes included. | The header becomes `Strict-Transport-Security: max-age=<default>; "max-age=31536000; includeSubDomains"`. It is malformed (duplicate directive, quoted token), and browsers may ignore the whole HSTS policy. | Use `hstsMaxAge=31536000` and `hstsFlags=includeSubDomains`, with no quotes. |

Other notes:
- `allowUnexpectedHost=true` and `checkOrigin=false` weaken security (Host-header and Origin validation are off). Keep them only if the LB/UAG topology really needs them.
- The file has CRLF line endings and no newline at the end. Both are harmless.
